# 架构说明

## 1. 分层模型

采用五层架构，层间依赖方向严格单向：

```
        ┌─────────────────────────────────────┐
        │   App   （组合根 / 面板装配）         │
        └─────────────────────────────────────┘
                          │
        ┌─────────────────┴───────────────────┐
        │   UI    （C++ 视图 / 图表 / 控件）    │
        └─────────────────────────────────────┘
                          │
        ┌─────────────────┴───────────────────┐
        │   Core  （生命周期 / 配置 / 服务）    │
        └─────────────────────────────────────┘
                          │
        ┌─────────────────┴───────────────────┐
        │   Domain（模型 / 差值运算 / 历史）    │
        └─────────────────────────────────────┘
                          ▲
        ┌─────────────────┴───────────────────┐
        │   Platform（原生 API 探针，只读计数器）│
        └─────────────────────────────────────┘
                          │
                    Windows 原生 API
```

## 2. 各层职责

| 层 | 职责 | 允许依赖 |
| --- | --- | --- |
| **Platform** | 封装 Windows 原生 API，**只返回累计计数器与能力标志，不做任何速率/百分比换算**。含进程枚举、系统计数器、磁盘、网络、GPU、电源、进程操作、路径提供者。 | Windows API、C++ 标准库、第三方工具库 |
| **Domain** | 把累计计数器转换为**差值、百分比、速率**；维护**有界历史环形缓冲**；处理计数器回绕、PID 复用、异常值钳制；产出**不可变快照**。 | 仅 Platform 的接口、C++ 标准库 |
| **Core** | 应用生命周期、主窗口管理、设置读写、路径服务、本地化服务、采样调度器、单实例互斥。 | Domain、Platform 的路径提供者 |
| **UI** | C++ 构建的视图、自定义控件、Win2D 图表、格式化与本地化。**绝不直接调用 Windows API。** | Domain 快照、Core 服务 |
| **App** | **唯一组合根**：创建 Platform 探针并注入 Domain 模型；装配各面板；协调采样节奏与选中状态。 | 全部下层 |

## 3. 硬性依赖规则

1. Platform 层返回原始计数器，Domain 层负责一切换算。**不得**在 Platform 层出现百分比计算。
2. Domain 层不得 include Platform 的具体实现，不得调用 Platform 的工厂函数。
3. UI 层与 App 层的渲染代码**不得** include Platform 的工厂头文件。
4. 探针（Probe）的创建只允许发生在 App 层的面板构造 / 初始化阶段（组合根），**禁止**在渲染循环中创建。
5. 所有 Windows API 调用必须收敛在 Platform 层。

## 4. 采样与快照管线

这是本项目性能目标的核心机制，必须严格实现：

1. **面板初始化**：各面板创建所需的 Domain 模型，注入 Platform 探针，执行一次
   **同步种子读取**（保证首帧有数据），随后把模型注册到后台采样器。
2. **后台采样器**：使用 `std::jthread` + `std::stop_token` + 条件变量，按配置间隔
   调用 `sample()`；刷新请求、间隔变更请求、停止请求都能**立即唤醒**，
   无需等待整个间隔。
3. **差值计算**：Domain 模型在采样锁保护下计算差值，产出以「PID + 进程启动时间」
   为键的快照，并更新历史。
4. **原子发布**：模型原子地发布**不可变、带版本号**的快照与历史「世代」（generation）。
5. **UI 渲染**：面板持有最新的发布世代，仅在**版本号变化时**重建过滤/排序缓存，
   渲染循环内**不加锁、不深拷贝**。

> **关键点**：进程枚举与重型系统指标（系统、磁盘、GPU）必须在后台线程执行。
> 目标是即使面对数千进程或高 IO 负载，UI 仍保持 60 FPS。

## 5. 进程身份与速率计算

- 进程状态以 **PID + 进程创建时间**为复合键。这样 PID 被复用时会自然产生新的基线，
  不会把两个不同进程的数据混算。
- 父子关系判定额外要求「候选父进程的启动时间 ≤ 子进程的启动时间」，
  避免 PID 在两次采样间被复用导致错误挂接。
- 必须防御：计数器回绕（新值 < 旧值）、超出合理范围的速率
  （如单进程 CPU 占用 > 100% × 核心数）、时间戳倒退。
- CPU 百分比 = 进程 CPU 时间增量 ÷ 系统总 CPU 时间增量。
- 磁盘 IO 与缺页速率 = 相邻两次采样的计数器差值 ÷ 时间间隔。
- 系统级与网卡级网络速率 = 相邻两次采样差值；**逐进程网络速率**为自首次观测基线
  以来的生命周期平均值（因数据源限制）。

## 6. 进程列表可扩展性

为在数千进程下维持 60 FPS：

- **稳定身份**：以 PID + 启动时间为键的缓存，正确处理 PID 复用。
- **后台建树**：进程树结构在 Domain 层的后台采样过程中构建，快照内直接携带
  预计算的子节点索引，**不在 UI 线程建树**。
- **缓存过滤与排序**：过滤/排序结果缓存，仅在数据版本号或过滤条件变化时重建。
  渲染循环复杂度严格为 O(V)，V 为可见行数。
- **UI 虚拟化**：进程列表必须启用 UI 虚拟化，只创建可见行的视觉元素。

## 7. 目录结构

```
src/
├── Platform/                  # 静态库 tmpp_platform
│   ├── Interfaces/            # IProcessProbe / ISystemProbe / IGpuProbe ...
│   └── Windows/               # Windows 原生实现
├── Domain/                    # 静态库 tmpp_domain
│   ├── Process/               # ProcessModel / ProcessSnapshot / 进程树
│   ├── System/                # SystemModel / CpuModel / MemoryModel
│   ├── Storage/ Network/ Gpu/ # 各子系统模型
│   ├── History/               # 环形缓冲
│   └── SamplingConfig.h       # 采样与历史的默认值与钳制范围
├── Core/                      # 静态库 tmpp_core
│   ├── Application.*          # 生命周期
│   ├── BackgroundSampler.*    # jthread 采样器
│   ├── Settings.*             # 配置读写
│   ├── PathService.*          # 路径解析
│   └── ...
├── UI/                        # 视图与控件（随 App 工程编译）
│   ├── Charts/                # Win2D 图表控件
│   ├── Controls/              # 自定义控件
│   ├── Formatting/            # 字节/速率/格式化
│   └── Views/                 # C++ 构建的视图类
└── App/                       # WinUI 3 可执行工程
    ├── App.*                  # Application 对象
    ├── MainWindow.*           # 主窗口与外层导航
    ├── UiHelpers.h            # 界面构建辅助
    └── StartupLog.h           # 启动诊断（临时）
```

> **当前状态**：M1-0 只建立了 `src/App`。其余目录将在对应里程碑中创建。

## 8. 界面构建方式（重要）

本项目的 UI **全部由 C++ 代码构建**，不使用 XAML。

原因与影响见 [BUILD.md 第 4 节](BUILD.md)。简要说明：本机 Visual Studio 缺失
原生 C++ XAML 构建所需的 `Microsoft.Windows.UI.Xaml.Cpp.targets`，
XAML 编译步骤无法挂载到 C++ 构建中。

由此产生两点架构约束：

1. **视图层是 C++ 类，不是 XAML 文件。** 各页面（进程 / 性能 / 详细信息）实现为
   继承自 `winrt::Microsoft::UI::Xaml::Controls::UserControl` 的 C++ 类。
2. **多语言不能用 `x:Uid` 自动绑定。** 必须通过代码中的 `ResourceLoader`
   显式取串（见 `docs/` 中的多语言说明）。

## 9. 容易踩的坑

- **WinUI 3 无法在服务窗口站运行。** 在 Session 0 或任何非交互式窗口站上，
  `Application::Start` 会在运行时内部 fail-fast，且**不产生任何有意义的错误信息**。
  排查时优先用 `query session` 确认会话类型。
- **`Application::Resources` 在构造期不可用。** 无 `App.xaml` 时，
  `XamlControlsResources` 必须在 `OnLaunched` 中合并，不能在构造函数中合并，
  否则抛出 `0x8000FFFF`。
- **不要使用预编译头。** WinUI 投影头会导致 PCH 膨胀至 1 GB 以上并触发 `C1076`。
- **C++/WinRT 运行时类不能是 `final`。** 生成的激活工厂会派生自实现类型。
